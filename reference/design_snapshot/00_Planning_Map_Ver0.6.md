# The Family — 콘텐츠별 시스템·UI 기획 구성과 검토 계획

**문서 ID:** PLAN-00  
**버전:** Ver0.6  
**작성일:** 2026-10-21  
**상태:** 문서 구성 검토안  
**승인자:** 사용자  
**현재 검토 단위:** SYS-02 이동 시스템·UI Ver0.2 · Map Tool 연계·구체 UI 검토  
**적용 대상:** The Family: Father of Steam

## 1. 문서 운영 원칙

하나의 콘텐츠 시스템을 규칙·진행·데이터·UI·UX·예외·검수까지 묶어 작성한다. 콘텐츠 시스템 기획서와 그 시스템의 UI 기획서를 별도의 독립 원본으로 운영하지 않는다.

사용자가 지정한 SYS-01~SYS-10의 이름과 기본 검토 순서를 유지한다. SYS-11~SYS-16은 누락 방지를 위한 추가 문서 제안이며, TOOL-01은 플레이 기능이 아닌 제작 지원 문서 제안이다. 추가 문서의 범위와 실제 진행 순서는 사용자 검토 전 확정하지 않는다.

한 문서의 주요 규칙과 해당 UI를 검토한 뒤 승인받고 다음 문서로 이동한다. 전체 시스템을 일괄 상세 작성하거나, 전체 HTML을 먼저 만들어 시스템 규칙을 역으로 맞추지 않는다. 현재 패키지에는 문서 구성안, 공통 작성 양식, SYS-01 승인본과 SYS-02 검토 초안을 제공한다.

### 제작 지원 문서 제안: TOOL-01

**기획 데이터·콘텐츠 제작 도구**: Excel 원본·필드 설명·식별자·참조·검사·JSON 생성·미리보기·오류 위치·배포 전 검사. 기획자가 게임 데이터를 편하게 작성할 작업 환경을 정의한다.

SYS-09는 이벤트 명령·분기·실행 의미와 이벤트 편집 동선을, SYS-10은 퀘스트 목표·완료·보상의 의미와 작성 동선을 소유한다. TOOL-01은 여러 콘텐츠가 공유하는 입출력·검사·변환·배포만 소유한다. Excel 외 별도 이벤트 편집기의 필요 여부와 구현 형태는 SYS-09 검토에서 제안·승인받는다.

## 4. 의존성과 순서 처리

### 기본 진행안 — 순서를 바꾸지 않는 권고

SYS-01 → SYS-02 → SYS-03 → SYS-04 → SYS-05 → SYS-06 → SYS-07 → SYS-08 → SYS-09 → SYS-10 순서를 유지한다. 추가 여섯 문서는 범위 승인 후 차례로 다룬다.

SYS-01에는 이미 승인된 연결 원칙과 공통 용어만 적는다. 예를 들어 공통 날짜와 전투 시간의 구분, 최대 파티 정원, 인물/아이템 식별, 처리된 결과의 재지급 금지, UI의 선택과 실행 구분이다. 실제 완납 즉시 엔딩·이후 메인 시나리오 진행 불가, 지정 메인 시나리오 이후 고아원 상환 차단, 10년 기한·미상환 게임오버·시나리오에 의한 기한 해제·주인공 사망/주요 시나리오 실패 가능성은 SYS-01 기준으로 유지한다. 상환 차단과 기한 해제는 동일 메인 사건에서 동시에 적용하며, 정확한 이벤트·퀘스트 상세를 미리 확정하지 않는다. 시간 산식·정확한 해제 Act·저장 시점·흥정률·조우 방식 등을 SYS-01에서 미리 확정하지 않는다.

각 단계에서 후속 문서가 소유한 미정 규칙이 필요하면 해당 부분을 `연계 규칙 결정 대기`로 표시하고 질문·권고안을 제출한다. 실제 정책을 테스트 코드에 숨겨 먼저 적용하지 않는다. 연결이 미정인 기능의 최종 완료를 주장하지 않으며, 의존하지 않는 현재 단계의 부분 검토는 가능하다.

### 실제로 선행 검토가 필요해질 경우

현재 단계에서 결정할 수 없는 의존 항목이 생기면 `선행 협의 대상 / 지금 필요한 이유 / 영향을 받는 단계 / 권고안 / 보류 시 가능한 작업`을 제시한다. 사용자가 승인하기 전에는 문서 순서를 바꾸지 않는다. 필요하다면 SYS-11 시간의 일부 또는 SYS-16 저장의 공통 정책만 앞당기며, 해당 문서 전체를 승인 없이 작성하지 않는다.

설계 순서와 코드 구현 순서는 같을 필요가 없다. 구현 순서를 정할 때에도 별도 검토한다. 단계별 기획 승인만으로 Godot 코드 작성·플러그인 설치·저장소 수정 권한이 부여되지는 않는다.

## 5. 문서와 규칙의 소유 경계

- **캐릭터**는 인물의 종류·기본/파생 변수·성장·관계/평판 대상·역할을 정의한다. 세력·지역 평판을 모든 캐릭터에 복사하지 않고 누구에 대한 누구의 평가인지 범위를 구분한다.
- **아이템**은 물품 정의·장비 개체·중첩·사용·장착·제작을 소유한다. **교역**은 거래 상품의 시장·가격·화물 원가·수탁 소유권·인계를 소유한다.
- **전투**는 행동·대상·효과·AI·승패·전투 목표의 판정을 소유한다. **파티**는 소속·슬롯·편성·현장 조작 자격을, **용병**은 영입·계약·비성장 특성을 소유한다.
- **이동**은 실제 위치·경로·차량 자산과 수송능력을, **파티**는 이용할 자산을 고르는 편성 문맥을 가진다. 차량 모델과 용량 공식을 두 곳에 독립 작성하지 않는다.
- **이벤트**는 조건을 검사해 씬 명령을 순서·분기로 실행한다. **퀘스트**는 목표 상태와 완료·보상 시점을 정한다. 둘 다 임의로 HP·화물·현금을 직접 중복 변경하지 않는다.
- **시간**은 모든 활동의 공통 시간 진행, **자금**은 실제 금전 반영, **저장**은 확정 상태의 기록·복원을 소유한다. 각 콘텐츠는 자신에게 필요한 변화만 요청한다.
- **조사**는 지식·증거 상태와 협력 판정을, **캐릭터**는 관계/평판 수치 또는 상태의 의미를 정의한다. 동일 신뢰를 별도 수치로 중복 만들지 않는다.
- **회복·휴식**은 숙소·생활 서비스와 회복 조건을, **아이템**은 회복약 사용을 소유한다. HP 상한의 정의는 캐릭터, 전투 중 회복 적용은 전투를 참조한다.

이 경계는 문서 조직안이다. 엔진 서비스나 클래스의 최종 분할을 승인한 것은 아니다.

## 6. 한 단계의 진행과 승인

| 순서 | 작업 | 검토 기준 |
|---|---|---|
| 1 | 범위·유지 결정·미정 사항 제시 | 이번 문서가 무엇을 소유하고 무엇을 다루지 않는지 확인 |
| 2 | 기능별 시스템+UI 초안 | 행동·조건·판정·효과와 표시·버튼·포커스·복귀가 같은 기능 아래에 있음 |
| 3 | 필요한 설계 선택 협의 | 근거·권고·대안·영향을 제시하고 결정 대기. 핵심 질문은 한 번에 하나씩 협의 가능 |
| 4 | 해당 기능의 읽기/조작 검토 | 필요한 화면 배치·목업만. 다른 미승인 시스템은 명시된 시험용 연결로 분리 |
| 5 | 문서 검토 및 승인 | 사용자가 승인 또는 수정 지시. 조건부 승인 항목은 해소 전 전체 확정으로 표시하지 않음 |
| 6 | 승인본 등록 후 다음 단계 | 현재 문서 대장에 범위와 버전 등록. 미정 연결은 별도 유지 |

문서 상태는 `초안 / 검토 / 확정`으로 구분한다. 세부 규칙은 `기존 확정 / 제안 / 결정 대기 / 수치 조정 대기`를 구분한다. 목업과 게임 검수는 `미작성 / 안내만 / 조작 시연 / 통합 검수`를 별도 표시한다. UI 콘셉트 승인과 기능 규칙 승인, 실제 구현 통과를 같은 상태로 합치지 않는다.

반복적인 목록 선택·이전 이동에 모든 단계마다 새로운 확인창을 붙이지 않는다. 사용자가 검토하는 문서 절차가 게임 플레이의 클릭 절차로 복제되어서는 안 된다.

## 7. 기능별 통합 명세의 최소 내용

1. 목적과 플레이어의 선택.
2. 진입·실행·사용 불가 조건.
3. 상태·변수·공식·효과와 저장할 값.
4. 정상·취소·실패·재시도·중단·복귀 흐름.
5. 같은 기능의 UI: 표시 정보·공개/숨김·공용 부품·행동 슬롯·포커스·오류 안내.
6. 기획 데이터: 정의 필드·허용값·참조·설명·테스트 사례. 숫자가 없으면 미정 또는 시험값을 명시.
7. 타 시스템에 요청·전달할 결과와 판정 소유자.
8. 정상 사례와 예외 사례의 검수 조건.

예: SYS-04의 `장비 교체` 절에서 장착 조건과 상태 변경을 설명한 직후 목록·후보 비교·적용/취소·능력치 미리보기·저장 복원을 설명한다. 같은 내용을 별도 장비 UI 문서에서 다시 정의하지 않는다.

## 8. 공용 UI 규칙의 위치

승인된 UI 지침 H-2 / M-1 / D-1 / B-1과 공용 행동 슬롯은 모든 콘텐츠 문서의 제약으로 사용한다. 공용 창·목록·버튼을 각 시스템마다 새로 디자인하지 않는다.

공용 부품의 규격은 재사용을 위한 하나의 원본에서 관리할 수 있다. 이는 시스템·UI 기획의 분리가 아니다. 각 콘텐츠 문서는 어떤 부품에 어떤 정보를 넣고, 언제 켜고 끄며, 버튼이 무엇을 실행하는지까지 반드시 기획한다.

정확한 치수·폰트·색상은 아직 승인되지 않았다. 승인된 것은 동일 템플릿에서 동일 역할의 위치·크기·입력을 일관되게 유지한다는 방향과 네 화면군 구성이다.

## 9. 변경과 아카이브

콘텐츠 문서는 현재 규칙·미정 항목·검수 상태만 담는다. 이전 사양 대비 설명과 변경 연혁은 본문에 누적하지 않는다.

개정 전 승인 스냅샷과 변경 사유·영향 문서 목록은 `archive/`에 보관한다. 원작 파일은 별도 보존한다. 아직 새 통합 문서가 승인되지 않은 시스템의 기존 자료를 무효화하거나 전체를 아카이브 완료로 표시하지 않는다.

현재 문서 대장은 승인본·검토본·미착수·추가 제안을 구분하고, 각 규칙의 기준 문서를 한 곳으로 지정한다. 단계 검토 중 다른 승인 문서의 규칙을 바꿔야 한다면 영향과 재검토 범위를 먼저 제시한다. 새 HTML의 시연값을 규칙 원본으로 승격하지 않는다.

## 10. 현재 단계와 검토 요청

[SYS-01 기본 시스템·UI](01_Basic_System_UI_Ver0.4.2.md)는 확정 기준이다. 현재는 [SYS-02 이동 시스템·UI](02_Movement_System_UI_Ver0.3.md)를 검토한다. SYS-03~SYS-10은 새 상세 문서 미작성이다. SYS-11~SYS-16 및 TOOL-01의 독립 문서 분리는 구성 제안으로 남긴다.

SYS-02는 지역 내부 직접 탐험 + 도시 간 노선 여정의 권고 접근을 채택했다. 현재 검토는 해당 이동의 구체 UI·조작 흐름과 Map Tool 대응 범위다. 카메라·충돌·좌표·추종·미니맵 등의 기술 세부는 실제 Tool 사양과 대조해 조정한다. 시험 기간·비용·수송량은 정식 정책이 아니다.

SYS-02는 보행·마을/실내·야외/던전·지도/상호작용을 먼저 다루고, 도시 간 이동과 운송수단을 같은 문서의 후반에서 연결한다. SYS-02 승인 후에만 SYS-03 캐릭터 시스템으로 진행한다.


## 현재 SYS-02 검토 경계

지역 내부 직접 탐험 + 도시 간 노선 여정이라는 권고 접근을 채택했다. 프로젝트용 Map Tool은 개발 중이며 실제 사양·출력물을 받아 공간·앵커·통행·카메라·지도·저장 참조를 조정한다. 현재 SYS-02 Ver0.2와 이동 전용 HTML 검토판을 검토하며, Tool 호환 또는 Godot 실기 검수를 통과했다고 보지 않는다. SYS-03은 아직 미착수다.

## 현재 이동 단계 산출물

도시 간 이동은 사용자 제공 구성안을 표시하는 월드맵에서 목적지를 지정한다. SYS-02 Ver0.3의 시스템·UI와 HTML Ver0.3을 검토한다. UI 지침 대조 결과는 `qa/UI_Guideline_Audit.md`에 분리 기록한다. Map Tool 연계·Godot 검수와 SYS-02 최종 승인은 별도다. SYS-03은 미착수다.
