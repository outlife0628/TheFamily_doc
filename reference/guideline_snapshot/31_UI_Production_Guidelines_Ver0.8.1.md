# 31. The Family — UI 제작 지침

**버전:** Ver0.8.1 · **작성일:** 2026-10-20  
**적용 대상:** The Family: Father of Steam의 UI 기획·아트·HTML 목업·Godot 구현·검수  
**문서 지위:** 공통 제작 원칙과 검수 요구의 기준. 화면군 콘셉트 H-2 / M-1 / D-1 / B-1은 사용자 승인 기준이다. 구체적인 치수·색상·최종 아트와 실제 품질은 별도 검토·검수 대상이다.

## 1. 제작 목표

**세계와 인물을 먼저 보여주고, 필요한 순간에 필요한 정보와 조작을 명확하게 제공한다.**

기본 RPG인 마을·필드 탐험, 대화·퀘스트 진행, 인카운터·전용 전투, 아이템·장비·회복·저장을 먼저 설계한다. 교역·운송·경영은 이 기본 플레이에 연결한다. 기능을 단순화하는 것과 시스템 규칙을 생략하는 것은 다르다.

탐험 HUD, 상세 메뉴, 대화, 전투는 서로 다른 정보 밀도를 갖는다. 전체 화면 메뉴의 넓은 정보 영역은 허용하지만, 그 정보량을 평상시 필드 HUD에 그대로 올리지 않는다. 화면을 덜 가리기 위해 글자를 작게 만드는 방법은 사용하지 않는다.

## 2. 근거와 설계 판단의 구분

2020년 이후 JRPG의 공식 소개·업데이트·개발자 인터뷰에서 확인한 사례를 참고한다. 모든 최근 JRPG가 같은 미니멀 스타일이라는 전제를 두지 않는다. 연구의 출처와 확인 한계는 [연구 근거](../reference/Research_Basis_Ver0.8.md)에 있다.

| 근거 유형 | 이 문서에서의 사용 |
|---|---|
| 사용자 지정 | 기본 RPG 선행, 공용 컴포넌트, 일정한 버튼·입력, 과한 화면 가림과 장식 억제, 여백·라운드·약한 반투명 |
| 공개 자료에서 확인한 사실 | FFVI PR의 불필요한 아이콘 표시 억제·미니맵 설정 유지, SO2R의 지도 이벤트 안내, 리버스의 명령 검토 모드 등 [R02][R03][R04] |
| 본작의 설계 판단 | 상황별 정보 분류, 템플릿과 공통 부품의 분리, 현재 파티 중심 정보, 상호작용 일관성 |
| 검토 수치·배치 | 폰트·모서리·알파·행 높이·배치 후보. 원작 실측값이나 검수 합격값이 아님 |

레퍼런스 화면을 보고 해당 게임의 내부 컴포넌트 코드나 상태 저장 방식을 단정하지 않는다. 비교 작품의 폰트·프레임·캐릭터 리소스를 추출하지 않는다.

위 원칙과 승인된 H-2 / M-1 / D-1 / B-1을 이후 UI 작업에 적용한다. 콘셉트 승인은 게임 규칙·수치·최종 아트 또는 구현 품질의 일괄 승인이 아니다.

## 4. 정보 노출 계약

모든 표시 항목은 `정보 원천 / 공개 조건 / 진입 조건 / 노출 위치 / 숨김 조건 / 지속 여부 / 다시 보는 경로 / 우선순위`를 갖는다. UI에는 플레이어가 알 수 있는 정보만 전달한다.

| 등급 | 정의 | 예시 | 필수 주의 |
|---|---|---|---|
| 기본 | 지금의 판단에 지속적으로 필요 | 전투의 이름·현재 HP·ATB·수동/자동·치명 상태 | '깔끔함' 때문에 핵심 정보를 감추지 않음 |
| 상황 | 접근·변화·문제 발생 때 필요 | 대화 가능, 목표 갱신, 획득물, 위험 상태 | 중요한 미해결 경고는 단순 시간 경과만으로 소멸시키지 않음 |
| 요청 시 | 읽기·비교를 위해 사용자가 연 정보 | 전체 퀘스트, 장비 후보, 원가 내역, 도시 지도 | 호버나 길게 누르기만을 유일한 접근 방식으로 두지 않음 |

HUD에는 현재 목적과 관련 없는 회사 장부·전체 파티 목록·채무 원금·대형 작품명을 상시 배치하지 않는다. 날짜·돈이 필요한 행동에서는 해당 문맥에서 반드시 보여준다. 실제 달력과 연동되지 않는 실시간 시계를 장식으로 만들지 않는다.

HUD는 '지금 할 일', 지도는 '공개된 목적지·경로', 일지는 '이유·조건·전체 진행'을 맡는다. 추적과 수락은 별개다. 새 목표 해금이 자동 수락·강제 추적·자동 장면 전환이 되어서는 안 된다. 연구의 지도 안내 사례를 참고하되, 미발견 단서나 미래 범인을 마커로 먼저 노출하지 않는다. [R03]

사용자가 선택한 미니맵·안내 표시 모드는 메뉴 복귀와 저장 복원에서도 유지한다. 강제 안내가 필요한 사건이라도 원래 설정을 기록하고 사건 후 복구한다. [R02]

## 5. 공용 컴포넌트와 템플릿

### 5.1 부품과 화면의 관계

`디자인 토큰 → 공용 컴포넌트 → 화면군 템플릿 → 공개 데이터·문구·행동 바인딩`의 순서로 구성한다.

전투, 퀘스트, 장비가 같은 큰 상자여야 하는 것은 아니다. 공통 부품의 글자·선택·버튼·입력 규칙을 유지하면서 배치 템플릿을 달리한다. 공용성은 배경을 복사하는 것이 아니라 상태·조작 계약을 재사용하는 것이다.

| 공용 컴포넌트 | 책임 | 바꿀 수 있는 내용 | 바꾸지 않는 규칙 |
|---|---|---|---|
| WindowSurface | 창 면·경계·모서리 | 승인된 크기 프로필·배경 변형 | 텍스트 알파, 프레임 계층 |
| ContextHeader | 화면 제목·선택 대상 | 장소·인물·탭 이름 | 제목 계층·문맥 순서 |
| TabStrip | 하위 범주 | 탭 이름·공개 여부 | 탭 이동 입력·포커스 표현 |
| SelectableList / ListRow | 목록 탐색 | 아이템·기술·의뢰·장비 | 행 높이 토큰, 선택/불가 상태 |
| DetailPane / ComparePane | 상세·전후 비교 | 효과·목표·증감·조건 | 숫자 정렬, 중요 결과 표시 |
| ActorStatusRow | 인물 상태 | 이름·HP·ATB·역할·상태 | 주요 인물/용병 식별, 값의 선명도 |
| TargetSelector | 실행 대상 검토 | 적·아군·장치·전체 범위 | 후보 이동·취소·확정 계약 |
| QuantitySelector | 수량 입력 | 최솟값·최댓값·단위 | 검사와 최종 확정 분리 |
| DialogueView / ChoiceList | 화자·대사·선택 | 일러스트·본문·선택 문구 | 읽기와 선택의 입력 분리 |
| ActionDock / ActionButton | 주·취소·보조 행동 | 이름·가능 여부·잠김 사유 | 슬롯 순서·크기·입력 |
| ConfirmDialog | 비용·효과의 최종 확인 | 거래·장착·수락·삭제 내용 | 한 모달, 배경 차단, 안전 초기 포커스 |
| QuestTracker / StatusNotice | 간단한 목표·문제 | 현재 행동·문제 요약 | 공개 상태·미해결 경고 보존 |
| Toast / ActivityRecord | 짧은 변화·기록 | 획득·완료·도착 | 중복 반영 금지·기록 재열람 |
| InputHint | 실제 입력 안내 | 키보드·패드 글리프 | 재지정된 의미 입력과 일치 |

화면군 템플릿은 FieldHUD(H-2), ListDetail/CompareDetail(M-1), Dialogue/Choice(D-1), BattleHUD(B-1)를 사용한다. Result와 Settings도 같은 공용 목록·상세·행동 슬롯을 사용한다. 세부 조립은 [승인된 콘셉트 기준](35_UI_Concept_Baseline_Ver0.8.1.md)을 따른다.

### 5.2 상태를 빠짐없이 설계

선택 가능한 행과 버튼에는 `기본 / 호버 / 포커스 / 선택됨 / 사용 불가 / 처리 중 / 오류` 상태가 필요하다. 호버는 선택이나 실행이 아니다. 비활성 사유는 마우스 호버 외에도 키보드·패드로 확인할 수 있어야 한다.

명령 권한과 상태 조회는 분리한다. 용병의 HP를 회복 대상으로 선택할 수 있다고 용병 수동 커맨드 창을 열지 않는다. 미공개 인물과 기술은 비활성 목록으로 예고하지 않는다.

## 6. 버튼·입력·행동 영역

### 6.1 필수 일관성

같은 의미의 행동에는 같은 논리 입력을 부여한다: `UI_CONFIRM / UI_BACK / UI_DETAILS / UI_AUX / UI_TAB_PREV / UI_TAB_NEXT`. 실제 키와 장치별 글리프는 입력 설정에 바인딩한다. 서로 다른 플랫폼의 A·X·○ 표기를 하나의 고정 이미지에 혼합하지 않는다.

동일 템플릿의 구매·장비·수락·보고 화면은 같은 행동 슬롯을 쓴다. 문구가 달라져도 버튼 위치를 다시 계산해 옮기지 않는다. 주 행동이 없거나 불가여도 취소가 주 행동 자리를 대신 차지하지 않는다. 레이아웃 공간만 보존할 수 있으며 의미 없는 비활성 버튼을 화면마다 억지로 만들지는 않는다.

리스트에서의 선택·대화 넘김처럼 빈번하고 가역적인 조작에 확인 모달을 추가하지 않는다. 비용·돌이킬 수 없는 효과가 있는 최종 행동만 적절한 확인 단계를 갖는다. 기획상 사전 확인이 이미 충분한 경우 동일 내용을 재확인하는 두 번째 모달을 붙이지 않는다.

### 6.2 공용 행동 슬롯 배치

승인 조합에는 다음 공통 역할 배치를 적용한다. 좌우 역할과 순서는 유지하며, 정확한 픽셀 좌표·폭·높이는 동일 템플릿과 글씨 프로필별로 배치 검토 후 고정한다.

| 위치 | 역할 |
|---|---|
| 하단 오른쪽 끝 | 주 행동: 사용·장착·수락·실행·계속 |
| 주 행동 바로 왼쪽 | 취소·이전·닫기 |
| 하단 왼쪽 | 보조 행동과 짧은 문맥 도움말 |
| 상단 고정 탭 영역 | 범주 전환 |

일반 창의 ActionDock는 화면 안전영역을 기준으로, 소형 모달의 ActionDock는 해당 모달을 기준으로 고정한다. 두 경우의 좌우 순서와 크기 프로필은 같다. 모달의 절대 화면 좌표가 메뉴와 다르다는 점은 템플릿 규칙으로 명시하고, 내용 길이 때문에 버튼이 이동하지 않게 한다. 이는 화면군을 넘어서도 모든 버튼이 물리적으로 같은 좌표라는 의미가 아니다.

탐험에서는 대형 결정 버튼을 상시 띄우지 않고 고정 HUD 안내 위치와 대상 근처 행동 표식을 쓴다. 대상 근처 표식은 대상을 따라가도 버튼의 의미·글리프는 바뀌지 않는다. 전투 명령창은 고정된 명령 영역을 사용하며 대상의 위치를 따라 움직이지 않는다.

### 6.3 입력 안전

본문만 스크롤하고 비용·핵심 결과·주 행동·취소는 스크롤 밖에 둔다. 한글 조합 중 Enter는 확정 명령이 아니다. 창 진입 직전 누르고 있던 결정 입력이 새 화면의 구매·수락까지 이어지지 않게 입력 해제를 기다린다.

되돌릴 수 없는 동작의 확인창은 안전한 취소에 초기 포커스를 둔다. 배경 입력을 차단하며 모달을 한 깊이로 유지한다. 닫을 때 이전 항목과 스크롤로 돌아온다. 닫힌 레이어에 포커스가 남거나 보이지 않는 버튼으로 이동하면 결함이다. [R07]

## 7. 네 화면군의 공통 한계선

| 화면군 | 반드시 지킬 것 | 금지할 것 |
|---|---|---|
| 마을·필드 | 길·상호작용 대상을 먼저 읽음, 공개된 목표 안내, 상태 이상 접근 | 전체 장부·8개 파티 전체 상태·대형 퀘스트 여러 개 상시 노출 |
| 메뉴 | 선택 대상과 비교 결과에 집중, 공용 목록·상세·행동 영역 | 퀘스트 화면에 무관한 전체 파티 상세를 고정 |
| 대화 | 화자와 한 대사, 인물 일러스트, 선택의 명확한 포커스 | 서로 다른 두 화자의 긴 대사를 동시에 읽게 함, 미공개 정체 예고 |
| 전투 | 최대 8명 이름·현재 HP·ATB·수동/자동·치명 상태를 동시 확인 | 4명만 보여주고 나머지를 스크롤/자동 대상으로 숨김, 턴 순서와 ATB 혼합 |

인원 수가 줄어도 파티 슬롯의 정체성은 유지한다. 파티 내부에서 UI가 임의로 '수동 4명/자동 4명'으로 재정렬하지 않는다. 권한은 인물·조작 문맥에서 계산한다. 주요 인물 1명+용병 7명, 주요 인물 2명+용병 6명 같은 구성을 검수한다.

HP와 ATB는 서로 다른 의미로 표시한다. '다음 턴'이라는 고정 순서표는 대기형 ATB의 확정 규칙이 아니다. 자원 슬롯은 승인된 자원만 사용하며, 용병에게 장비·레벨·경험치·빈 SP 게이지를 장식으로 붙이지 않는다.

대화·메뉴·전투 명령을 읽는 현실 시간은 운영 날짜로 환산하지 않는다. 직접 전투에서 수동 명령을 고르는 동안 적·용병·상태·전장 목표의 논리 시간이 함께 멈춘다.

## 8. 시각·크기 프로필

### 8.1 공통 시각 언어

저채도의 남청·슬레이트 면, 밝은 문자, 얇은 경계, 제한적인 선택 강조를 우선한다. 청색·은색의 정확한 색상값은 아트 콘셉트 단계에서 결정한다. 황동과 톱니는 세계 속 역·배관·운송수단·도구에 두고, 기본 버튼과 창의 상시 테마로 확대하지 않는다.

한 화면의 활성 조작 대상은 한 곳이다. 전투에서 현재 행동 인물, 선택할 목표는 서로 다른 기호로 함께 표시할 수 있지만 두 개의 키보드 포커스를 만들지 않는다. 모든 창 가장자리를 발광시켜 선택 표시와 경쟁시키지 않는다.

약한 반투명은 창의 면에만 적용한다. 본문의 가독성이 부족하면 불투명도를 높이거나 국소적인 어두운 배경을 사용한다. 강한 블러·반사·유리 왜곡을 기본 요구로 하지 않는다. 고대비 선택에서는 불투명 면을 허용한다.

### 8.2 검토용 시작값 — 최종값 아님

아래 숫자는 본작의 비교용 출발값이다. 참고 게임 실측값·공식 최소 규격·상용 검수 합격값으로 인용하지 않는다.

| 항목 | 시작 후보 | 판단 기준 |
|---|---|---|
| 설계 해상도 | 1920×1080 | 사용자 지정 |
| 기본 본문 | 28px | 한글의 실제 몸통·줄간격과 최종 출력으로 검수 |
| 확대 프로필 | 100/125/150% | 200% 대응은 별도 확장 검토; 150% 검사만으로 접근성 인증을 주장하지 않음 |
| 대화 본문 | 32~36px | 읽을 줄 수와 얼굴·선택지의 공간 충돌 확인 |
| 버튼 높이 | 기본 64px / 확대 80~96px 후보 | 같은 프로필에서 모든 동일 역할 버튼 통일 |
| 버튼 폭 | 기본 208px / 확대 264~312px 후보 | 가장 긴 현지화 문구로 공통 폭을 선정 |
| 모서리 | 10~16px 후보 | 부드럽지만 과도하게 둥근 모바일 카드형을 피함 |
| 면 알파 | 0.90~0.96 후보 | 실제 합성 배경에서 대비 확인, 고대비 1.0 |
| 테두리 | 1~2px 후보 | 작은 UI를 두꺼운 프레임으로 감싸지 않음 |
| 목록 행 | 기본 64px부터 내용에 따라 공통 프로필 선정 | 행마다 제각각 축소하지 않음 |
| 바깥 여백 | 72~120px 범위에서 템플릿별 선정 | 화면 가림과 내용 밀도를 실제로 비교 |

폰트 크기의 CSS/엔진 지정값과 실제 글자 몸통 크기는 다르다. XAG 101의 수치를 그대로 한글 폰트 크기에 대입하지 않는다. 중요한 오류·툴팁·입력 글리프도 본문 확대 정책을 따른다. [R08]

본문 명도 대비 4.5:1을 내부 검토 시작 목표로 두되, 합성 배경에서 실제 측정한다. 색만으로 이익·손실·선택·위험을 구분하지 않고 부호·문구·도형을 병행한다. 이는 본작 QA 목표이며 접근성 인증이 아니다. [R09]

### 8.3 화면 확대와 재배치

글씨를 늘렸을 때 일반 목록은 한 방향 스크롤이나 별도 상세 단계로 재배치한다. 필수 결과와 행동 영역을 밀어내지 않는다. 8인 전투 상태는 인원을 숨기는 대신 영역 높이 또는 승인된 확대 전용 배치를 사용한다.

프로필을 바꾸면 시각적 배치와 포커스 이동 순서를 함께 바꾼다. 전투 중 매 행동마다 창의 위치가 달라지는 것은 허용하지 않는다. 기기 화면이 작다고 낮은 해상도로 구운 글자를 확대해 쓰지 않는다. 지도에는 공개 지점의 목록 탐색도 제공한다. [R07]

## 9. 세계관과 데이터의 표현 경계

시드리아는 세 종족의 공동도시다. 시계탑 광장·시장·중앙역·고아원·산업지구·수로·지하 시설 등 장소의 차이를 배경과 현장 아이콘으로 전달한다. 기본 UI 부품을 종족별로 전혀 다르게 만들지는 않는다. [P01]

크리스·브람·올리버는 청소년 인물이며 엘리아나는 원작의 연령·문화 설정을 따른다. 생성 이미지 속 임의 인물명·중년 초상·레벨·턴 표기를 정식 캐릭터나 게임 규칙으로 쓰지 않는다. 얼굴과 일러스트는 승인된 아트로 교체 가능한 리소스다. [P02]

놀란·그레타·네리아는 고정 사업 직원이다. 직원 정보창의 존재가 이들을 전투·상인 파티원으로 영입한다는 뜻은 아니다. [P04]

Act 1의 시작 가능 알림은 강제 시작과 다르다. 조사 화면은 알 수 있는 질문·증거만 제공하며, 숨겨진 지하자원이나 후반 배후 인물을 빈칸·아이콘·툴팁으로 먼저 노출하지 않는다. [P03][P05]

원작 테마와 현재 사용자 결정의 역할을 구분한다. 기본 RPG 선행 제작은 가족·사업·조사의 서사적 중요성을 삭제하지 않는다. 현재 공통 파티·상인 조건·자동 사업·직접 교역 규칙은 독립된 시스템 기준으로 보존한다.

## 10. 화면별 필수 명세와 완료 기준

각 화면은 [작성 양식](../templates/UI_ScreenSpec_Template.md)을 사용해 다음을 기록한다.

`목적 → 진입 → 표시 정보 → 조작과 포커스 → 실제 판정 → 상태 변화 → 취소·실패 → 저장·복귀 → 검수 사례`

명령 버튼 뒤에 공통 설명문만 나오면 해당 기능은 '안내만 제공'이다. UI 시제품 완성에는 실제 후보·선택·비교·확정/취소·결과가 필요하다. 시스템 계산이 미정이면 명확히 표시한 시험 데이터로 UI를 검토하되 정식 게임 규칙으로 승격하지 않는다.

목업은 화면 카탈로그의 독립 장면 열람과 실제 연결 동선을 구분한다. 기본 검증 동선은 **마을 NPC → 대화·퀘스트 수락 → HUD 갱신 → 현장 이동·조사 → 전투 → 결과·목표 갱신 → 보고·보상 → 저장·재개**다.

원작 퀘스트를 테스트할 때에는 개업 전 자유 생계와 정착지 열차 사건의 서사 순서를 임의로 바꾸지 않는다. 테스트용 별도 시나리오가 필요하면 'UI 검증 전용'이라고 명시한다.

## 11. 제작 순서와 적용 절차

**승인된 콘셉트 확인 → 기본 RPG 시스템의 정보·입력 명세 → 장식 없는 배치 → 공용 부품 → HTML 연결 시제품 → 아트 적용 → Godot 실제 입력 검수** 순으로 진행한다.

작업자는 시작할 때 이 문서, 승인된 콘셉트 기준, 해당 시스템 명세를 함께 읽는다. 소스 루트에 [AGENTS.md](../AGENTS.md)를 인수인계용으로 제공한다. 이는 사용자 PC·저장소·다른 대화에 자동 배포되었다는 뜻이 아니다.

새 UI마다 부품을 추가하기 전에 기존 컴포넌트로 표현할 수 있는지 확인한다. 기존 부품으로 표현 불가한 차이가 있다면 그 기능·입력·접근성 이유를 명시하고 변형을 등록한다. 단순한 장식 차이만으로 새로운 구현을 만들지 않는다.

현재 문서는 현재 기준과 미정 사항만 보관한다. 변경 이유·이전 스냅샷·비교 이미지는 배포용 기준 본문 밖의 아카이브에서 관리한다. 역사 문서가 화면 제작의 기본 입력이 되어서는 안 된다.

## 12. 검수 게이트

[UI 검토 체크리스트](../qa/UI_Review_Checklist_Ver0.8.1.md)를 사용한다. 검사 증거는 비교할 수 있는 화면 캡처·입력 로그·표시 영역 값·상태 전후 값으로 남긴다.

1. 정보 게이트: 공개·필수·상황·요청 정보가 구분되어야 한다.
2. 조작 게이트: 동일 역할의 위치·크기·입력과 취소 복귀가 일관되어야 한다.
3. 읽기 게이트: 실제 한글·큰 수치·8인·큰 글씨로 검사한다.
4. 연결 게이트: 수락·사용·장착·전투·보상이 실제 상태와 연결되어야 한다.
5. 제품 게이트: 승인된 아트, 실제 Windows·Godot·컨트롤러에서 검수한다.

이번 문서는 규칙과 체크리스트를 만든 산출물이다. 화면 제작·브라우저·엔진·사용자 플레이 검수가 통과했다고 표시하지 않는다.
